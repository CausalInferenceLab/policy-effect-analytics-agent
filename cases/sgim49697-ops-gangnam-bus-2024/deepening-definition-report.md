# 공개 시간 명세와 과거 응답 샘플로 확인한 것

T Data의 `dataprovide` 화면에서 **2021년 응답 샘플**을 추가 확인했다. 첫 탐색의 빈 출력인자 샘플 칸과는 별도 영역이다. 그러나 이번에 읽은 공개 명세만으로는 OA-21217의 초/분 단위, 정차 포함, 시간대 배정 사건, 평균 분모를 확정할 수 없다. 시간 지수를 실제 분 단위 절감으로 바꾸거나 정차·주행 시간으로 분해하는 작업은 보류한다.

## 명세와 샘플의 대응

| 공식 화면 | 출력 명세 필드 | 별도 JSON 예시 필드 | 예시 기준일 | 확인 범위 |
|---|---:|---:|---|---|
| [1039 노선·구간 운행시간](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=1039) | 59 | 59 | 2021-12-17 | 밑줄·대소문자를 정규화하면 필드명이 모두 대응 |
| [1083 정류장 운행 통계](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=1083) | 32 | 34 | 2021-12-18 | 예시에 `partKey`, `prtitnKey` 두 필드가 추가됨 |
| [1084 차량 운행 통계](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=1084) | 40 | 42 | 2021-12-18 | 같은 두 추가 필드가 있으며 차량·회차 관련 키가 있음 |

세 화면 모두 요청에 인증키와 기준일을 요구한다. 월 1회 갱신 안내와 과거 예시가 있다고 해서 현재 2023~2025년 전체 응답을 받을 수 있다고 판단하지 않았다. 인증 신청이나 실제 API 요청은 하지 않았다. 예시의 차량번호·차량 ID는 공개 산출물에 다시 싣지 않았다.

출력인자의 개별 샘플 칸은 세 화면 모두 비어 있다. 1039·1084는 값 설명도 전부 비어 있고, 1083의 값 설명 세 칸은 분류 코드다. 필드명이 대응한다는 것은 **표기 대응**이며 OA-21217과의 계산식·원천·단위 동등성은 별도 문제다.

## 숫자가 있어도 단위가 확정되지 않는 이유

1039 예시는 일 시간값 35, 0~3시 값 34·38·37·29, 4시 값 0을 포함한다. 해당 예시에서 속도와 운행 이용횟수는 `null`이다. 시간 0과 공란의 생성 규칙, 시간 평균의 가중 분모는 설명되지 않는다. 하나의 예시를 실제 API 전체의 결측률이나 표본 분포로 취급하지 않는다.

1084의 예시에서는 출발 시각 12:54:42와 최종 시각 13:32:40의 차이가 2,278초이고 `tourTime`도 2,278이다. **이 한 예시가 초 단위 해석과 일치한다는 정도의 산술 확인**이다. 다른 필드인 1039 `tripTime`이나 OA-21217의 시간값에 그 단위를 옮겨 적용하지 않는다. 최종 시각이 도착·정차·출발 중 무엇인지도 이 값만으로 정할 수 없다.

더 큰 문제는 `stpcarTimeAcmtl`의 설명이다. 1083에는 통과 시간의 누적 건수로, 1084에는 정차 시간의 누계로 표시된다. 예시 값도 각각 검출 건수와 같지만 이 관계를 정의로 사용하지 않는다. 정차·개문·통과 필드를 단순 합산하거나 여행시간에서 빼면 중첩 구간·다른 분모를 섞을 수 있다. [앞서 확인한 공개 파일 83](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=83)과의 헤더 불일치도 함께 해결되어야 한다.

## 현재 확정할 수 있는 분석 경계

- [OA-21217 공식 설명](https://data.seoul.go.kr/dataList/OA-21217/S/1/datasetView.do)은 날짜·시간·노선·정류장 간 평균이라는 집계 수준을 확인해 준다. 현재 D+5 적재와 최근 30일 API 제공 안내는 과거 월 파일의 당시 이용 가능 시각과 구분한다.
- 1039의 시간·속도·횟수·정류장 순서가 분리된 구조와 과거 예시가 존재하는 것은 확인했다. 이것만으로 현재 로컬 CSV의 단위나 산출식을 검증하지 않았다.
- 1083·1084는 정차·개문·통과·검출 건수·차량/회차 분해의 자료 후보가 된다. **정의와 실제 과거 자료 확보 전에는 분해 결과를 만들지 않는다.**
- 현재 보유한 일/시간 집계로는 차량별 배차간격 분산, 승객별 대기시간, 같은 차량의 구간 합을 만들 수 없다. [시간·횟수 공동 기록 감사](deepening-cohort-report.md)는 이 한계를 없애지 않는다.

## 다음 확인 요청에 넣을 구체적 질문

1. `tpss_route_section_speedh`와 1039가 2023~2025년에 같은 산출 테이블이었는가? 시간·속도·횟수 각각의 단위와 평균 분모는 무엇인가?
2. 구간의 시작·끝 사건은 무엇이며 어느 정류장의 정차·개문·신호 대기가 포함되는가? `h07`은 어떤 사건의 시각으로 배정되는가?
3. 0·음수·공란·행 부재, 같은 노선의 정류장 재방문, 날짜 적재 실패를 어떤 규칙으로 구분하는가?
4. 1083의 `stpcarTimeAcmtl` 설명은 건수인가 시간인가? 1084·파일 83과의 대응 및 검출 건수별 분모는 무엇인가?
5. 1083·1084의 과거 보관 범위와 실제 접근 절차는 무엇인가? 익명 차량·회차·시각을 연결할 수 있는가? 현재 접근 가능 여부와 2024년 당시 공개 시점을 구분해 달라.

이 문서는 질문을 정리한 것이며 기관이나 다른 사람에게 발송하지 않았다. `"tpss_route_section_speedh" 초`, `"TPSS" "운행시간" "초"`, `"trip_time_07h" "단위"`의 추가 검색에서는 결과를 얻지 못했다. 이는 공식 정의가 어디에도 없다는 결론이 아니다.

## 재현

사례 폴더에서 다음 명령은 저장한 공개 HTML의 해시를 확인하고 표·예시 대응만 다시 계산한다. 미래 연도 예시, 모호한 정규화 대응, 표 구조 변경은 오류로 처리한다.

```bash
.venv/bin/python deepening.py definitions-audit
```
