## 연구 질문

**2024년 6월 29일로 안내된 강남대로 광역버스 운행 조정 이후, 평일 퇴근 시간대 일반 차량의 교통 흐름은 비교 도로에 비해 어떻게 달라졌는가?**

정책의 대상과 안내상 시행일은 [서울시 정책 안내](https://mediahub.seoul.go.kr/archives/2011484)를 출발점으로 삼는다. [TOPIS 도로별 통행속도](https://topis.seoul.go.kr/refRoom/openRefRoom_1.do)를 이용해 개선과 악화 양쪽 가능성을 검토한다. 버스 승객의 이동시간이나 교통정책 전체의 편익을 직접 평가하는 프로젝트는 아니다.

## 문서 읽는 순서

| 문서 | 용도 |
|---|---|
| [기본 계획](plan.md) | 확인된 근거, 분석 방향, 미정 사항과 진행 기록 확인 |
| [외부 AI 조사·검토 요청서](research-request.md) | 파일 전체를 복사해 외부 AI에 전달. 이 README나 대화 기록 없이도 조사할 수 있는 요청서 |

주 분석은 평일 퇴근 시간대로 정했다. 정확한 시간 범위, 전후 기간, 대상 링크, 비교 도로, 주 지표와 추론 방법은 외부 검토 후 확정한다. 실행용 `plan.yaml`과 수집 코드는 아직 없으며, 이 문서 묶음은 **사전 등록 완료나 분석 결과를 뜻하지 않는다.**

## 작업 위치와 저장소 관례

[기여 가이드](../../CONTRIBUTING.md)의 개인 케이스 폴더와 `<GitHub ID>/<작업>` 브랜치 규칙을 따른다. 사람이 읽는 계획과 조사 문서를 개인 폴더에 두는 방식은 [기존 계획 문서](../YoungjaeKang-retail-hours/plan.md)를 참고했다. 계획과 수집·결과 단계를 나누는 방식은 [녹색교통지역 사례](../yesolee-green-traffic/README.md)를 참고했다. 다른 사례의 분석 내용이나 결과를 가져오지는 않는다.

이번에는 세 문서만 준비한다. [멘티 참여 가이드](../../docs/ops/mentee-guide.md)의 작업 제안 이슈와 프로젝트 등록은 외부 검토를 반영한 정식 계획 제출 단계에서 함께 진행한다. 현재 작업 제안 이슈·프로젝트 등록·PR은 없으며, 사이트에 등록된 분석이나 완료된 계획으로 표시하지 않는다.

## 다음 진행 순서

1. `research-request.md`를 외부 AI에 전달하고 조사 답변을 받는다.
2. 답변의 원문 출처를 직접 확인한 뒤 `plan.md`의 근거·미정 사항과 진행 기록을 갱신한다. 출처 없는 제안은 확인된 사실로 옮기지 않는다.
3. 처치 구간·비교군·기간·지표·제외 기준·검정과 판단 보류 조건을 정하고 작업 제안 이슈를 작성한다.
4. 저장소 스키마에 맞는 `plan.yaml`과 `catalog/projects.yaml` 등록을 준비한다. 주제 분류가 맞지 않으면 새 주제를 제안한다.
5. 결과 열람·분석보다 먼저 계획을 커밋하고 계획 PR을 제출한다. 저장소의 사전 등록 기록 기준에 맞춰 결과 커밋과 하루 이상 간격을 둔다.
6. 계획 검토 후 수집기와 검증을 구현하고 실제 분석을 수행한다. 원자료·가공 데이터는 커밋하지 않는다.

## 문서 단계 검증

저장소의 `make check`와 문서 링크·출처·변경 범위를 확인한다. 실행 명령과 결과는 [계획의 진행 기록](plan.md#진행-기록)에 남긴다. 분석 효과를 계산하는 `make flow`는 실행용 계획을 확정한 다음 단계에서 사용한다.
