# 원주사랑상품권 할인 상향과 결제 변화 분석 계획

**작성자: whatfontisthis · 트랙 B 가설과 분석 · 2026년 10월 18일 초안 · 10월 19일 제출 준비**

우리가 알아보려는 것은 **“상품권을 더 싸게 살 수 있게 해주면, 그 상품권으로 결제하는 돈이 늘어날까?”**예요. 첫 사례는 2024년 9월 원주시예요. 당시 모바일 원주사랑상품권의 구매 할인이 7%에서 10%로 올라갔어요. 예를 들어 10만 원짜리 상품권을 살 때 내는 돈이 9만 3천 원에서 9만 원으로 줄어드는 셈이에요.

이 폴더는 **계산 전에 비교 규칙을 검토받기 위한 계획 초안**이에요. 아직 과거 결제자료를 받거나 비교도시를 확정하거나 효과를 계산하지 않았어요. 작업 제안 이슈에서 주제와 막힌 부분을 공유하고, 두 파일은 Draft PR로 검토를 요청해요. Draft는 아직 완성하지 않은 초안이라는 뜻이에요.

작업 제안과 자료 확보에 관한 질문은 [이슈 24번](https://github.com/CausalInferenceLab/policy-effect-analytics-agent/issues/24)에 정리했어요.

## 1 무엇이 언제 바뀌었나요

- 공식 근거는 **원주시공고 제2024-2250**이에요.
- 공고기간은 2024년 8월 21일부터 9월 30일까지예요.
- 시행일은 **2024년 9월 2일 오전 10시**예요.
- 대상은 **모바일 원주사랑상품권의 구매 할인**이에요.
- 할인율은 **7%에서 10%로 3%포인트** 올라갔어요.
- 2024년 9월 동행축제와 추석을 위한 한시 혜택이에요.

[원주시 공식 공고](https://www.wonju.go.kr/www/selectBbsNttView.do?bbsNo=140&key=216&nttNo=444171)

공고기간의 마지막 날이 실제 판매 종료 시각이라는 뜻은 아니에요. 판매 종료, 조기 매진, 추가 발행, 구매한도, 사용처와 다른 지원의 변화도 확인해야 해요. 상품권을 산 날과 가게에서 쓴 날이 다를 수 있다는 점도 기록해요.

## 2 무엇을 비교할까요

**질문:** 원주시 모바일 상품권 할인 상향 기간에, 혜택 조건이 안정적이었던 비슷한 다른 도시와 비교해 원주의 주간 모바일 상품권 결제금액이 어떻게 달라졌을까요?

원주의 할인 전후 변화에서 비교도시의 같은 기간 변화를 함께 고려해요. 이렇게 변화의 차이를 보는 방법이 **이중차분**이에요. 도시마다 원래 다른 점과 모든 도시에 공통인 주별 변화도 계산에서 고려해요. 비교도시에는 같은 무게를 줘요.

가장 먼저 볼 값은 `log(1 + 주간 결제금액)`이에요. 로그는 금액 규모 차이를 다루기 위해 숫자를 바꾸는 계산 방식이에요. 원 단위 금액과 그래프도 함께 보여줘요. 결제횟수는 함께 살펴보는 지표예요. 금액과 횟수 중 결과가 좋은 쪽으로 주 지표를 바꾸지 않아요. 증가·감소·불확실을 모두 보고해요.

## 3 어떤 기간을 볼까요

한 행은 **도시 하나의 일주일 기록**이에요. 월요일부터 일요일까지 묶어요.

| 구간 | 기간 | 주 번호 | 쓰는 방법 |
| --- | --- | --- | --- |
| 변경 전 | 2024년 6월 3일부터 8월 18일 | 0부터 10 | 11주를 기본 비교에 써요 |
| 미리 소식을 들었을 수 있는 때 | 8월 19일부터 9월 1일 | 11과 12 | 기본 계산에서 빼고 그래프에는 따로 보여줘요 |
| 변경 후 | 9월 2일부터 9월 29일 | 13부터 16 | 4주를 기본 비교에 써요 |
| 그 이후 | 9월 30일 이후 | 기본 표에 넣지 않아요 | 혜택 복귀와 잔액 사용을 확인하는 참고자료로만 봐요 |

주 번호는 제외한 기간 때문에 다시 매기지 않아요. 변경 시작은 13주차예요. 첫 주에는 시행일 오전 10시 전 기록도 섞일 수 있으므로 9월 2일부터 8일까지를 뺀 결과도 살펴봐요. 월별 자료만 있다면 이 주간 분석을 실행하지 않아요.

## 4 어떤 도시와 비교할까요

**최종 비교도시는 미확정이에요.** 춘천·강릉·충주·제천은 공식 공고와 자료를 찾아볼 후보일 뿐, 적합하다고 확인한 곳은 아니에요. 이 네 곳만으로 비교를 확정하지 않아요.

다음 조건으로 일반시를 더 찾아 **비교도시 5곳 이상**을 확보해요.

1. 2024년 혜택 변경 전 인구가 원주의 절반부터 두 배 사이인 일반시를 먼저 조사해요. 인구 출처와 기준일도 남겨요.
2. 같은 기간에 같은 뜻의 모바일 결제자료가 있어야 해요. 시·군·광역시의 구나 모바일·종이·전체 상품권 자료를 임의로 섞지 않아요.
3. 할인율, 구매한도, 발행 지원, 사용처 제한이나 자료 제공 방식이 크게 바뀐 곳은 제외해요. 추석과 동행축제 추가 혜택도 확인해요.
4. 원주와 가까워 소비 이동이 생길 수 있는 곳은 기본 비교에서 제외하거나 따로 살펴봐요.
5. 변경 전부터 움직임이 크게 다르거나 근거가 부족하면 효과 판단을 보류해요. 원하는 답이 나오는 도시만 골라 남기지 않아요.

5곳은 우리 작업의 최소 기준이고 통계적으로 충분하다는 보증은 아니에요. `min_clusters: 20`은 공용 프로그램의 도시 수 경고 기준이에요. 경고를 없애려고 이 숫자를 5로 낮추지 않아요.

## 5 어떤 자료가 필요할까요

| 자료 | 필요한 내용 | 현재 확인 수준 |
| --- | --- | --- |
| [조폐공사 결제정보](https://www.data.go.kr/data/15108292/openapi.do) | 지역, 결제일, 모바일 유형, 금액·횟수, 환불·제공기관 범위 | 소개만 확인, 2024년 실제 응답은 미확인 |
| [조폐공사 판매정책정보](https://www.data.go.kr/data/15125217/openapi.do) | 지역별 할인 시작·종료일, 할인율, 구매한도와 상품권 유형 | 소개만 확인, 과거 이력은 미확인 |
| 원주와 비교도시의 공식 공고 | 시행일, 발행액·행사·사용처 등 함께 바뀐 조건 | 원주 주 공고 확인, 나머지는 조사 필요 |
| 지역 번호와 인구 자료 | 2024년 지역 구분과 규모 | 실제 코드와 인구 원표 확인 필요 |

API는 컴퓨터가 자료를 받는 창구예요. 인증키가 필요하면 로컬 `.env`에서만 관리해요. 두 조폐공사 자료의 소개에는 이용허락범위가 ‘제한 없음’으로 표시돼 있어요. 특정 공공누리 유형으로 추정하지 않고 계획에는 `license: other`와 근거를 적어요. 추가 자료의 이용 조건은 각각 확인해요.

자료를 받을 때는 전체 합계와 세부 내역을 두 번 더하지 않아요. 못 받은 값과 실제 결제 0을 구분해요. 환불로 음수가 나온 값은 임의로 지우거나 로그를 취하지 않고 정의부터 확인해요. 모든 지역에 동일한 주가 있고, 중복·누락·상품권 종류 변화가 해결돼야 해요.

## 6 계산을 시작하기 전에 확인할 것

다음은 프로그램의 형식 검사와 별도로 사람이 확인해야 하는 조건이에요. 확인 전에는 `make flow`로 효과를 계산하지 않아요.

- [ ] 2024년 6월부터 9월까지 일별 또는 주별 모바일 결제자료를 실제로 받았어요.
- [ ] 원주와 적격 비교도시 5곳 이상의 명단과 정책 이력을 문서에 확정했어요.
- [ ] 모바일·카드의 중첩과 기관별 합계 중복, 환불·정산일 정의를 확인했어요.
- [ ] 원주 1곳과 비교도시 모두에 변경 전 11주, 변경 후 4주의 같은 시점이 있어요.
- [ ] 기본 표에서 주 번호 11·12를 빼고, 13~16만 변경 후로 사용해요.
- [ ] 변경 전 추세, 명절·행사·발행 조건과 인접 지역 영향을 검토했어요.
- [ ] 자료와 프로그램의 이용 조건, 비교 방법을 멘토와 검토했어요.
- [ ] 최종 명단과 규칙을 효과 계산 전에 커밋했어요.

한 조건이라도 해결되지 않으면 그 사유를 적고 실행을 보류해요. 비교도시 목록을 확정하기 전 이 계획은 **미확정 항목이 있는 초안 PR**로 검토를 요청해요.

## 7 결과가 우연인지 다시 확인해요

| 확인할 것 | 방법 | 공용 프로그램에서의 처리 |
| --- | --- | --- |
| 실제 변경 전에도 차이가 생기나요 | 7월 22일부터 8월 18일까지를 가짜 변경 후 4주로 놓아요 | `placebo_time`, `shift: 6`으로 계획해요 |
| 바뀌기 전부터 다르게 움직였나요 | 변경 전 11주의 그래프와 추세를 확인해요 | 현재 `did` 경로는 사전추세 검정을 자동 실행하지 않으므로 별도 확인해요 |
| 한 도시 때문에 결과가 달라지나요 | 비교도시를 하나씩 빼고 다시 계산해요 | 현재 공용 실행 흐름은 `drop_unit`을 자동 실행하지 않아 별도 분석으로 남겨요 |
| 첫 주 때문에 결과가 달라지나요 | 변경 후 첫 주를 빼고 다시 계산해요 | 별도로 계산해요 |
| 안내 이후 미리 움직였나요 | 뺀 2주를 따로 보여주고 포함한 결과도 비교해요 | 기본 결과와 구분해서 계산해요 |
| 금액과 횟수가 함께 움직이나요 | 같은 조건으로 결제횟수도 봐요 | `outcomes`에 보조 지표로 적어요 |

가짜 변경 날짜는 실제 변경 주 번호 13에서 6을 빼서 7, 즉 2024년 7월 22일이에요. 기본 표에서 주 번호 11·12를 미리 빼야 가짜 변경 후도 4주가 돼요. 가짜 변경 전은 7주뿐이라 확인의 힘이 약해요. 차이가 안 나왔다고 정책 효과를 증명했다고 말하지 않아요.

현재 `did` 실행에서는 최소 사전 기간 경고도 자동으로 계산되지 않아요. 위의 11주 확인을 직접 해야 해요. 스키마에 이름이 들어 있다고 해당 점검이 모두 자동 실행되는 것은 아니에요.

## 8 어떤 결론까지 말할 수 있을까요

상품권 결제가 늘어도 소상공인 전체 매출이나 새로 늘어난 소비라고 해석하지 않아요. 할인과 동행축제·홍보·발행 조건이 겹치면 할인율 하나의 효과라고 분리하지 않아요.

원주 한 곳만 혜택을 바꾼 사례라서 독립적인 실험이 여러 개 있는 것도 아니에요. 공용 코드가 도시를 바꿔 비교하는 계산을 하더라도, 그렇게 바꿔도 되는 이유를 설명할 수 있어야 해요. 오차 범위가 작다는 이유만으로 확정적 효과를 주장하지 않아요.

자료 누락, 비교도시 부족, 변경 전 추세 불일치, 다른 정책과의 혼합, 불안정한 결과는 **판단 보류 또는 판단 불가**로 남겨요. 신뢰할 수 있는 계산 범위에 0이 들어가면 ‘효과 없음’ 대신 ‘방향이 불확실함’으로 설명해요. 자료를 못 구하면 무엇이 부족하고 어디서 더 찾아야 하는지 정리해요.

## 9 어떤 순서로 검토받을까요

우선 이 폴더의 두 파일만 준비해요. 실제 자료 수집은 계획 검토 뒤 `fetch.py`로 만들고, 해석은 계산 뒤 `discussion.md`에 적어요. 현재 수집 프로그램이나 결과 파일이 있는 것처럼 제출하지 않아요.

1. 최신 참여 안내에 따라 작업 제안 이슈에 트랙 B와 이 주제를 적어요.
2. `whatfontisthis/plan` 브랜치에서 이 폴더의 두 파일을 커밋해요. 커밋은 파일의 변경 이력을 저장하는 일이에요.
3. 자료와 비교도시가 미확정임을 밝힌 Draft PR을 작업 제안 이슈와 연결해요.
4. 검토 의견과 실제 자료 확인 결과를 반영해 명단과 규칙을 확정하고, 효과를 계산하기 전에 다시 커밋해요.

## 기술 참고와 검사 범위

10월 18일 초안은 공용 저장소의 `5886f0c4b857328c982e01081988def571822b24` 버전으로 형식 검사를 통과했어요. 10월 19일 제출 기준은 최신 `main`의 `9a9faadf579bc83fac509d16068bac59b012c7b8` 버전이에요. 폴더 이름과 `case_id`, 변경 전 11주·변경 후 4주, 가짜 시점 비교의 7주·4주와 주 번호를 다시 확인했어요. 원자료와 API 키는 포함하지 않아요. 실제 자료 확보와 효과 계산은 아직 하지 않았어요. 형식 검사와 공용 테스트 통과는 실제 분석 성공이나 설계 승인과 구분해요.

Python 3.11 환경에서 `make check`와 같은 구성인 `python -m ruff check .`와 `python -m pytest -q`를 실행해 통과했어요. 추가로 계획 스키마, 날짜 계산, 로컬 링크, 라이선스와 데이터 계보 검사를 통과했어요. 선택 기능 관련 테스트 2개는 건너뛰었고, 실제 원주 자료를 쓰는 `make flow`는 실행하지 않았어요.
